---
name: counterfact-analyze
description: Suggest a Counterfact analysis after editing an agent's prompt, skills, or tool definitions, or help when the user asks to analyze an agent.
---

After editing an agent's prompt, skills, or tool definitions, suggest an analysis and wait for the user to ask for it.

If the user replies to a question with a question, answer it in plain words first, then ask again if still needed. If the reply isn't one of the options, respond to what they said. Never answer a question with only another question.

If Counterfact's tools are missing because its MCP server failed to connect, tell the user in one line: "Run /mcp and reconnect counterfact, or restart Claude Code." Don't fall back to the shell (see below).

To fix a finding, read it with `get_finding` (pass its id or `findingId` as `id`), then propose an edit using its explanation, quoted lines, and suggested fixes. Edit only the files the finding quotes; if they are outside the chosen folder, say so before editing. If the finding cannot be identified, ask which one they mean. Fix only what the user agreed to.

When the user asks for an analysis:

Before analyzing, identify the agent, its folder, and its files from what you already know of the repository. Treat `CLAUDE.md`, `AGENTS.md`, and similar files as instructions for coding agents, not as the agent to analyze, and leave them out of the file list. Stop and ask which agent to analyze only if there are several candidates or none.

1. Inspect the available Counterfact tool schemas. If `sign_in` has no `email` parameter, `sign_in_with_code` is absent, or `sign_in_status` has no `path` parameter, use this browser sequence: Call `sign_in_status` first without `path`. If not signed in, tell the user: "Counterfact needs you to sign in once (free, no card)." Call `sign_in` without arguments. When it returns a link and code, always show both. If it opens a browser, say: "Opening your browser… If nothing opens, go to <pageUrl> on any device and enter <userCode>." Otherwise say: "Go to <pageUrl> on any device and enter <userCode>." Then call `sign_in_status` with `wait: true` and no `path`; signing in on another device works while it waits. Don't start an analysis until the user is signed in. If all email tools and parameters are available, call `sign_in_status` first with `path` set to the chosen agent folder. If not signed in, tell the user: "Counterfact needs you to sign in once (free, no card)." Prefer the email address you already have for the signed-in user in your own context. Otherwise use `suggestedEmail` from `sign_in_status`, when present. Do not search files, contacts, or other services for an address. Show: "By signing in, you agree to our Terms of Service (https://counterfactlabs.com/terms) and Privacy Policy (https://counterfactlabs.com/privacy)." If you have an address, ask: "Sign in to Counterfact as <address>, or use a different address?" If you have no address, ask: "What email address would you like to use to sign in to Counterfact?" Wait for the user to confirm the offered address or supply another one. Only then call `sign_in` with `email` set to that address. Never send a code just because you found an address. After a successful send, ask: "Enter the code from your email." Wait for the user's code, then call `sign_in_with_code` with the same confirmed email and that code. Never repeat the code in your messages, logs, or reports. If the code is wrong, show the returned message and ask the user for the code again; do not send another code automatically. If it expired or there were too many attempts, show the returned message and wait for the user to ask for a new code before calling `sign_in` again with the confirmed email. If sign-in is rate limited, show the returned message and wait; do not retry automatically. If email sign-in is unavailable, show the returned message and ask: "Use browser sign-in instead?" Use browser sign-in only if the user requests or accepts it: call `sign_in` without `email`. When it returns a link and code, always show both. If it opens a browser, say: "Opening your browser… If nothing opens, go to <pageUrl> on any device and enter <userCode>." Otherwise say: "Go to <pageUrl> on any device and enter <userCode>." Then call `sign_in_status` with `wait: true` and the chosen folder's `path`; signing in on another device works while it waits. After successful email sign-in, call `sign_in_status` with the chosen folder's `path` to refresh `signedIn` and `analyzeToolAllowed`. Don't start an analysis until the user is signed in.
2. After sign-in, call `waiting_fixes` if available. For a `local:<name>` key, treat the item as belonging to the open workspace when `<name>` exactly matches the chosen agent folder's name (or the launch folder's name for file inputs) or the workspace root folder's name. For an `owner/repo[/folder]` key, match `owner/repo` against the open repository's Git remote using known facts or read-only Git metadata, and require any scoped folder to be inside the open workspace. Offer only matching items, and show each item's `repoKey` exactly as returned, even when finding numbers are unique. Do not offer or claim items from another repository or with a missing `repoKey` or uncertain repository identity. If only a `waitingFixes` count is known, or no items match, skip the offer and continue with step 3. For matching items, mention them once in one line: "1 fix is waiting: F-10 <title> (<repoKey>). Fix it now?" Name each item by the number or id and title the tool's text shows; also include its project when two matching items share a number. For several matching items, put them in the same line: "2 fixes are waiting: F-10 <title> (<repoKey>), F-12 <title> (<repoKey>). Fix one now?" Wait for the user's answer to that offer. If they agree, call `claim_fix` with the selected matching item's `findingId` as `id`, then fix it as described above. Then, whether they declined or after the fix, continue with step 3 to analyze the chosen agent. Do not repeat a waiting-fix offer the user already accepted or declined in this conversation.
3. If `analyzeToolAllowed` is false and you haven't asked in this conversation, first state Counterfact's own wording verbatim: "Counterfact says: The analysis runs on your computer. Model requests go encrypted to Counterfact's sealed relay, which we can't read into. Your sign-in token, repository facts, file names and sizes, and findings with code quotes are sent to your console. Only agent files from the folder you choose are sent; secret and ignored files are skipped."
4. Then, under the same condition, ask separately: "Allow Counterfact's analysis tool from now on, so auto mode doesn't stop it?" On yes, add `mcp__plugin_counterfact_counterfact__analyze_agent` to `permissions.allow` in `~/.claude/settings.json`, keeping everything else in the file. Use Claude Code's normal settings edit; Claude Code will ask the user to approve that edit. If the edit is refused or blocked, tell the user they can add it themselves: run `/permissions`, choose Allow, and add that rule. On no, continue without it.
5. When the user asks for an analysis, show the agent's name and file list in a few lines, then call `analyze_agent` without asking for approval of the list, using `path` for one selected agent file or folder, or `paths` for several selected agent files, according to the available tool schema; use the agent's folder as `path` when the schema supports only folders. Pass `proposal` with `agentName` and `files`, giving each file a `path` relative to the selected folder for folder inputs or to the launch folder for file inputs, and a `role` of `prompt`, `tools`, `model-calling code`, `config`, or `other`. Counterfact treats the proposal as a strong hint and still checks every file. Each call runs one analysis and charges the user's balance at the listed price, so call it only when the user has asked, and don't ask them to approve a price first. Never call a preview tool for a price or pass `confirm`. If the balance doesn't cover it, show the returned message, which includes the top-up link. If the tool cannot tell which folder holds the agent, ask the user which of the returned candidate folders holds it, then call `analyze_agent` again with their answer as `path`, making the proposal's paths relative to that folder and leaving out files outside it.
6. The tool returns findings and a link. Show the full-results link to the project's findings page, then list every returned finding as the tool's text lists it, keeping its order and group headings. Read a finding with `get_finding` using its returned id only when the result has no title or you need its details to judge seriousness.
7. Only after showing the full list, offer to fix the most serious finding, preferring ones that affect the agent's users. If the user agrees, fix the chosen finding as described above. Do not call `claim_fix` for new findings from an analysis.

Only use Counterfact's tools for sign-in and analyses. Never run `counterfact-labs` or `npx @counterfact-labs/cli` in the shell from Claude Code.

Use `get_balance` when the user asks about their balance or needs a top-up link.

An analysis can take several minutes. Claude Code cancels a tool call after 15 minutes. If the tool call is cancelled or times out, the analysis stops. Run it again only when the user asks.
